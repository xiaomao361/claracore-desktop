Two acceptance numbers in this plan were wrong as written and are corrected in
place below:

- **A1 was self-contradictory.** The 23-tool candidate `core` manifest
  serializes to 14,231 bytes with unchanged descriptions and schemas, already
  over the stated 12 KB ceiling. Reaching 12 KB requires compressing
  descriptions and narrowing advertised schema properties, not only reducing
  tool count. The ceiling stands; the tool-count ceiling moves to 26 so
  `memoria_link_create` and `memoria_record_create` stay in the normal surface.
- **A3's 240-byte candidate preview did not fit its own 4 KB payload ceiling**
  once the preview is carried in both the message text and the structured
  candidates. The implemented preview bound is 160 bytes, which satisfies "at
  most 240" and keeps a five-candidate refusal at 3,413 bytes.

## 1. Objective

v0.6.6 makes ClaraCore Desktop a more selective Agent context layer. It does
not remove Memoria, Shared Line, or InnerLife capabilities. It separates rich
stored state from the smaller packet that an Agent needs for one decision.

The work has two independent but coordinated tracks:

1. **MCP interface context:** reduce the tool definitions, onboarding text,
   documentation, and error payloads that a connected host may place in model
   context before any product data is read.
2. **Everyday product context:** reduce the Memory, Shared Line, InnerLife, and
   aggregate context returned during normal recall and continuation work.

The release succeeds when normal Agent use is materially smaller, relevant
context remains available through progressive disclosure, and full diagnostic
or historical detail is still explicitly retrievable.

### 2.3 Automatic-injection boundary

The Codex host hook currently calls `memory_context` and reviews pending
InnerLife shares at each non-empty user prompt. It adds content only when:

- Memory Controller returns `policyMode=canary`, `action=INJECT_TOP1`, and a
  non-empty bounded context; or
- one pending InnerLife share passes the timing gate for review/use.

Shared Line is not automatically injected as a full packet. A history or
continuation cue asks the Agent to query it selectively.

The automatic path is smaller than the explicit read paths, but it has no
single cross-domain winner or shared total-byte budget. Memory and InnerLife
can both qualify in one turn, and a timing candidate can still be semantically
irrelevant after deterministic review.

## 3. Design Principles

1. **Storage richness is not delivery richness.** Stored history, profile,
   affective trace, and diagnostic metadata may remain complete while default
   Agent reads stay small.
2. **Progressive disclosure is the product contract.** Default reads answer the
   next decision; explicit detail reads expose the supporting record.
3. **One fact has one default representation.** Do not return the same material
   as full structured fields, extracted subfields, and a second large text
   block in one response.
4. **Stable state is loaded by scope.** Agent-level state is not repeated in
   every line-level packet. Session-level state is not repeated in every turn.
5. **Automatic context has one winner.** Memory, Shared Line, and InnerLife
   compete for one bounded delivery slot instead of stacking independently.
6. **Bytes are a testable acceptance metric.** Tests assert serialized UTF-8
   byte ceilings. Token estimates remain diagnostic because tokenizer behavior
   belongs to the receiving host/model.
7. **Full detail remains explicit.** Maintenance, diagnosis, history review,
   and UI detail must not be weakened to satisfy the normal Agent budget.
8. **Identity and evidence boundaries remain unchanged.** Authenticated caller
   identity, same-Agent canary filtering, sensitivity, time view, ambiguity
   refusal, delivery evidence, and read-only behavior remain fail-closed.

## 4. Track A: MCP Interface Context

### A1. Introduce tool profiles

Classify the existing 84 tools into two maintained profiles:

- `core`: normal connection, recall, continuation, selective sharing, and the
  minimum writes needed during ordinary work;
- `full`: the complete maintenance, import/export, graph, retention, identity,
  daemon, archive, diagnostics, and advanced editing surface.

The first-party Agent Setup path uses `core`. Existing clients can explicitly
select `full` through a maintained HTTP header or stdio environment setting.
The exact transport key must be frozen in the first implementation slice and
tested on both transports. An unidentified or invalid profile fails to `core`,
not to the larger surface.

Gateway tool input is not schema-validated anywhere, so `inputSchema` is purely
advertisement to the model. `core` therefore narrows both the tool list and the
advertised property set of some tools, while every handler keeps accepting the
full argument set and every tool still executes when called by name. That is
what makes the 12 KB ceiling reachable without removing capability.

Implemented `core` manifest (25 tools, `core/gateway/tool-profiles.js`):

- connection/context: `claracore_connection_test`, `claracore_status`,
  `gateway_docs`, `gateway_context`;
- Memory: `memory_context`, `memoria_search`, `memoria_get`, `memoria_create`,
  `memoria_update`, `memoria_link_create`, `memoria_record_create`;
- Shared Line: `shared_line_list`, `shared_line_get`, `shared_line_create`,
  `shared_line_activate`, `shared_line_update`,
  `shared_line_handoff_create`, `shared_line_agent_state`;
- InnerLife: `innerlife_session_start`, `innerlife_session_end`,
  `innerlife_status`, `innerlife_pending_shares`, `innerlife_share_check`,
  `innerlife_mark_share`, `innerlife_submit_inbox`.

The implementation may remove a candidate only with a startup/use-case test;
it must not add maintenance tools merely for symmetry.

`memoria_link_create` and `memoria_record_create` were added to the original
candidate list because the first-party Agent instructions require them for
ordinary work (link after writing a fact; log structured recurring records).
Leaving them out would have made the default profile contradict the documented
workflow.

The frozen transport keys are `X-ClaraCore-Tool-Profile` (HTTP) and
`CLARACORE_TOOL_PROFILE` (stdio).

Acceptance:

- `core` exposes no more than 26 tools;
- serialized `core` `tools/list` is at most 12 KB;
- `full` preserves all existing tool names and schemas unless a separately
  documented contract change is required;
- HTTP and stdio identify the selected profile truthfully;
- Agent Setup generates the first-party `core` configuration;
- invalid or missing profile configuration never broadens authority.

### A2. Make Gateway documentation progressive

Change `gateway_docs` from one full handbook into a small default summary plus
explicit sections such as:

- `start`
- `memory`
- `shared-line`
- `innerlife`
- `diagnostics`
- `full`

The default response contains connection truth, the three domain roles, the
safe startup sequence, and links/arguments for deeper sections. It does not
repeat every tool description already available through `tools/list`.

Acceptance:

- default `gateway_docs` is at most 4 KB;
- each section is independently bounded at 8 KB;
- default docs plus `core` tool descriptions contain no contradictory startup
  sequence;
- existing onboarding safety statements remain represented;
- docs reads remain observational and create no product content.

### A3. Bound error and recovery payloads

Ambiguous Shared Line errors return at most five candidates by default, each
containing only id, title, status, updated time, and a bounded summary preview.
Return total count and a paging/detail reference for the rest.

Apply the same rule to large validation and recovery errors: return code,
reason, next safe action, and bounded evidence instead of embedding a catalog.

Only `error.message` crosses the MCP boundary, so the bounded previews must
travel in the message text as well as in the structured candidates. Hosts that
read JSON-RPC `error.data` now receive the structured refusal on both
transports.

Acceptance:

- default ambiguity response is at most 4 KB;
- candidate preview is at most 240 UTF-8 bytes (implemented at 160, because the
  preview is carried twice and five candidates must still fit 4 KB);
- no line is guessed or mutated;
- an Agent can retrieve the complete catalog explicitly.

### A4. Keep onboarding one-time

The copied Agent Setup text remains a connection artifact, not a recurring
system prompt. It points to the small docs/startup path and does not reproduce
the full Memory Controller or module playbooks.

Acceptance:

- copied setup text is at most 4 KB excluding generated credentials/config;
- it distinguishes connected, context read, automatic injection, and actual
  use;
- it does not claim that MCP connectivity proves per-prompt host injection.

## 5. Track B: Everyday Product Context

### B1. Memory: summary-first recall

`memory_context` keeps the current authenticated, current-time, same-Agent,
normal-sensitivity, top-one canary boundary. The explicit `memoria_search`
contract changes to summary-first retrieval:

- default `limit=3`, with an explicit bounded override;
- default result contains id, title, bounded body preview, labels, state role,
  relevance/source, and updated time;
- embedding provider/model/dimension/error fields move behind diagnostic
  detail;
- related records are omitted by default and retrieved explicitly;
- `memoria_get(id)` remains the full-record path;
- historical/all views remain explicit.

Acceptance:

- default three-result search is at most 6 KB;
- ordinary search does not expose embedding operational metadata;
- the top result and temporal state semantics match the pre-change result;
- `memoria_get` preserves the full body and reviewable metadata;
- Memory Controller retains the 600-token soft target and 900-token hard
  limit already established for a valid automatic hit;
- current, historical, restricted, superseded, and same-Agent tests pass.

### B2. Shared Line: a real resume packet

Add maintained detail levels:

- `resume` (default): the smallest packet needed to continue work;
- `context`: resume plus relevant Shared Reality;
- `full`: historical, diagnostic, and compatibility detail.

Default `resume` fields:

- line id and title;
- current summary and interpretation status;
- facts used;
- next step;
- updated time;
- at most one recent handoff summary when present.

Default `resume` excludes:

- `agentState`;
- all Agent states;
- model adjustment unless a model is explicitly requested;
- snapshots and multi-entry position history;
- affective trace;
- raw position metadata;
- large parallel text that repeats structured fields.

Agent state remains available through the existing
`shared_line_agent_state` tool. It should be loaded once per Agent session or
after an observed update, not once per Shared Line read. Model adjustment
remains an explicit model-scoped read.

Acceptance:

- default `shared_line_get` is at most 4 KB;
- `agentState` is absent from the default line packet;
- two unrelated lines do not repeat Agent-level preferences or boundaries;
- `context` contains only non-empty relevant Shared Reality fields;
- `full` preserves history, snapshots, handoffs, managed arcs, and agent state
  where compatibility requires it;
- ambiguity, confirmed-overwrite protection, line identity, and one-current-
  position-per-line semantics remain unchanged.

### B3. InnerLife: status, candidates, and briefing are distinct

`innerlife_status` becomes operational state only:

- counts;
- daemon state;
- doctor summary/issues;
- booleans/counts indicating pending shares and Inbox work;
- detail references.

It does not return pending Inbox bodies or a 20-item share catalog by default.

`innerlife_pending_shares` defaults to three candidates with bounded previews.
Full share body is returned only when one share is explicitly inspected or
passes `innerlife_share_check` for possible delivery.

`innerlife_briefing` becomes a decision-oriented synthesis rather than an
aggregate dump. Its default form may include:

- selected Shared Line summary, when unambiguous;
- compact current interests/open loops;
- counts for Inbox and candidate material;
- at most one selected share preview or recommended next read.

It does not simultaneously return five full Memories, five full shares, five
Inbox bodies, and five thoughts. It must not return the same body in both
thought and share collections.

Acceptance:

- default `innerlife_status` is at most 3 KB;
- default `innerlife_pending_shares` is at most 3 KB;
- default `innerlife_briefing` is at most 6 KB;
- no exact body appears twice in one briefing;
- pending content remains pending until explicit delivery/review action;
- status and briefing reads do not create profiles, sessions, shares, or
  content;
- full detail remains available through explicit records/detail calls.

### B4. Aggregate Gateway context

`gateway_context(detail=brief)` composes only the new default contracts:

- one Shared Line resume packet;
- up to three Memory summaries, or one query-relevant Memory by default;
- InnerLife status plus at most one candidate preview;
- bounded guidance and detail references.

It returns one canonical representation. If structured fields are retained,
the text field is a genuinely small summary rather than a second copy of all
content. `detail=full` remains explicit and is not used in startup guidance.

Acceptance:

- brief context is at most 8 KB, with a stretch target of 5 KB;
- no field family is represented more than once without an explicit reason;
- selected Agent and Shared Line identity are preserved;
- no cross-Agent Inbox/share content enters the packet;
- ambiguous line selection stays an explicit safe result;
- query and no-query paths meet the same byte ceiling.

### B5. One automatic-context winner

Introduce a host-side context arbiter for automatic Memory and InnerLife
delivery. Shared Line remains an explicit read unless a future host contract
proves a bounded automatic resume use case.

The arbiter records candidates but delivers at most one block:

1. discard invalid, restricted, historical, cross-Agent, stale, or weak
   candidates;
2. compare relevance and urgency across eligible Memory and InnerLife results;
3. select one winner or abstain;
4. enforce the total byte/token budget;
5. preserve selected, delivered, used, ignored, wrong, corrected, and unknown
   as separate evidence states.

Acceptance:

- at most one automatic ClaraCore block enters a user turn;
- total automatic context has a 600-token target and 900-token hard limit;
- a Memory hit prevents a second InnerLife block in the same turn unless a
  future explicit policy changes the one-winner rule;
- irrelevant timing candidates can be rejected without being marked used;
- response-completion evidence is required before claiming delivery/use.

## 6. Measurement And Regression Contract

Add a maintained context-budget smoke that serializes representative product
fixtures and emits machine-readable JSON containing:

- tool/profile counts and schema bytes;
- docs and error bytes;
- Memory result count, body bytes, metadata bytes, and related bytes;
- Shared Line bytes by current position, Shared Reality, Agent state, history,
  snapshot, arc, and text;
- InnerLife bytes by status, profile, shares, Inbox, thoughts, and briefing;
- aggregate Gateway brief/full bytes;
- automatic candidate, selected, and delivered bytes.

The smoke fails on default-surface ceilings. Full/admin payloads are measured
and reported but do not share the normal-use ceiling.

Use deterministic fixtures for CI. Use a read-only live-runtime audit only as
supplemental evidence; live personal content and counts are not committed.

Required semantic regression assertions:

- current truth is not replaced by stale history;
- same-Agent and sensitivity boundaries remain fail-closed;
- Shared Line ambiguity never guesses or writes;
- removing default `agentState` does not delete or mutate it;
- InnerLife candidate reads do not mark delivery;
- full/detail reads recover every field intentionally removed from defaults;
- read-only fingerprints stay unchanged after context inspection.

## 7. Implementation Order

Each phase is a small validated loop. Do not combine all domains into one broad
rewrite.

### Phase 0: Freeze evidence and tests — done

- `scripts/context-budget-baseline.js` emits the machine-readable report
  (`npm run baseline:context-budget`);
- `core/tests/fixtures/context-budget-ceilings.js` holds every Track A and
  Track B ceiling in one place;
- `core/tests/fixtures/context-budget-fixtures.js` holds deterministic
  fixtures; no live personal content or counts are committed;
- `core/tests/context-budget-smoke.js` enforces the default-surface ceilings and
  runs inside `npm run check`.

### Phase 1: MCP core profile and docs — done

- `core/gateway/tool-profiles.js` implements `core`/`full` selection, shaping,
  and fail-closed resolution;
- `core/gateway/docs.js` replaces the single handbook with a bounded default
  plus six sections, and drops the duplicated tool manifest;
- `ambiguousSharedLineError` in `core/db/helpers.js` bounds the refusal;
- `app/views/agent-setup.js` and the `/agent/setup` payload distinguish
  connected, context read, automatic injection, and actual use;
- both transports resolve and report the profile
  (`core/gateway/mcp-server.js`, `electron/http-agent-gateway.js`).

Test contracts that asserted the pre-0.6.6 defaults were updated rather than
weakened: `phase2-gateway-smoke`, `phase3-gateway-smoke`,
`phase4-gateway-contract-smoke`, `streamable-http-gateway-smoke`, and
`agent-access-ui-smoke` now assert the core manifest, then re-assert the entire
full manifest under an explicit `full` profile.

### Phase 2: Memory summary-first contract — done

- `memoria.searchSummary` in `core/memoria/index.js` adds summary/detail
  shaping: default `limit=3`, bounded body previews, no embedding operational
  metadata, related records omitted;
- the explicit override is bounded at 25, not unlimited;
- `memoria_get`, `detail="full"`, and the temporal/sensitivity paths are
  unchanged, and the Desktop UI and `gateway_context` ports still read the full
  record.

### Phase 3: Shared Line resume contract — done

- `core/continuity/resume-detail.js` implements `resume`/`context`/`full`;
- `agentState`, all agent states, snapshots, arcs, raw position metadata, and
  the parallel `text` block leave the default read;
- `omitted` reports the true size of what was left out plus the detail
  reference, so the Agent knows an arc exists without paying for it;
- write acknowledgements (`shared_line_update`, `create`, `activate`,
  `handoff_create`) return the same resume shape.

The strict fixture also exposed a real defect: `nextStep` was the one unbounded
field in the packet, at 76 KB in the worst case. It is now bounded like every
other field.

### Phase 4: InnerLife selective contracts — done

- `core/innerlife/selective.js` separates status, candidates, and briefing;
- status returns counts, daemon, doctor, and pending-work indicators, not a
  20-item share catalog and five Inbox bodies;
- candidates are bounded previews, three by default, and listing marks nothing;
- the briefing is a decision synthesis and drops any thought body that
  duplicates a share body, which the live audit found three of.

### Phase 5: Aggregate context and automatic arbiter — done (server side)

- `gateway_context(detail=brief)` composes the new default domain contracts:
  one Shared Line resume packet, up to three Memory summaries, InnerLife status
  plus at most one candidate preview;
- the `text` field is now a genuinely small orientation summary and is asserted
  not to repeat any structured body;
- `core/gateway/auto-context.js` implements the one-winner arbiter with the
  600/900-token shared budget, recorded discard reasons, and separate evidence
  states. It is exposed as `gateway_auto_context`.

**Scope note:** the plan framed the arbiter as host-side. The host hooks for
Codex, Claude, and Hermes live outside this repository, so the arbitration
logic is implemented here as one tested module and exposed through the Gateway
rather than duplicated per host. **Those hooks still need to be pointed at
`gateway_auto_context`; until they are, no behavior changes in a live host
turn.** That work is not done and is not claimed as done.

### Phase 6: Integrated acceptance and release decision

- run focused and full regression;
- update architecture, code map, playbooks, version truth, and release notes;
- bump `package.json` and `package-lock.json` together only after the behavior
  is accepted as the `0.6.6` checkpoint;
- package, install, sign, notarize, tag, push, and publish only with separate
  authorization and completed release evidence.

## 8. Validation Matrix

Minimum focused validation by track:

| Boundary | Required checks |
| --- | --- |
| MCP profiles/docs/errors | `npm run test:context-budget`, `npm run test:gateway:http`, `npm run test:agent-access` |
| Memory | new Memory payload tests, `npm run test:phase2`, `npm run test:memory-controller` |

| InnerLife | new status/briefing budget tests, `npm run test:phase5` |
| aggregate/automatic | `npm run test:context-budget`, Gateway context performance smoke, HTTP/stdio contracts, hook-specific injection smoke (pending: hooks are out of repo) |

Passing source tests does not prove the installed App, signed package, release
asset, or real host integration.

## 9. Compatibility And Migration

- no database schema migration is expected for context shaping alone;
- stored Memory, Shared Line, Agent state, model adjustment, and InnerLife data
  remain intact;
- full-profile and explicit-detail paths preserve advanced workflows;
- changed defaults must be called out in `AGENT_MCP_PLAYBOOK.md`,
  `MULTI_AGENT_CLIENTS.md`, Gateway docs, and release notes;
- existing clients that depend on large default payloads must select `full` or
  explicit detail during the compatibility window;
- do not silently reinterpret `lite` as a different historical contract:
  introduce named detail levels, test them, and deprecate old assumptions
  explicitly.

## 10. Non-Goals

v0.6.6 does not:

- delete or compact personal data merely to reduce Agent context;
- merge Memoria, Shared Line, and InnerLife into one store or one lifecycle;
- replace SQLite;
- redesign Desktop pages unless contract truth requires small copy/state
  updates;
- claim that selected context was used without host response evidence;
- make full diagnostic payloads satisfy the normal-use byte ceilings;
- publish a release merely because the source implementation passes.

## 11. Completion Criteria

The `0.6.6` implementation is ready for a release decision only when:

- both Track A and Track B default payload ceilings pass deterministically;
- the core tool profile is the first-party default and the full profile remains
  explicitly available;
- Memory, Shared Line, InnerLife, and Gateway semantic regression passes;
- automatic context delivers at most one bounded relevant block or abstains;
- read-only paths create no product state;
- docs describe the exact default/detail/profile contracts;
- the full source suite passes;
- version, package, installed runtime, signing/notarization, and publication
  layers are reported separately and truthfully.
