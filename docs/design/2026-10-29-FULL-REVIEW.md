## 已证实问题，按优先级排序

### R1 · P1 · 搜索过程中切换智能体，旧结果仍显示在新筛选下

**影响/触发**：A 智能体搜索尚未返回，用户切到 B。筛选已变 B，但 A 的结果仍被渲染；B 的搜索被 `searchPending` 直接丢弃。容易误认记忆归属。这是同一本机页面中的筛选错配，不是已证明的访问权限绕过。

**证据**：`app/memoria-actions.js:15–45,56–59` 只有互斥标志，没有请求版本或回执身份核对。`app/views/memoria.js:213–233` 的搜索结果路径直接接受传入 rows。受控 Promise 复现：可见筛选 B，只请求 A，落地结果 agentId=A。

**建议**：以 query + agentId + 请求序号验证回执；筛选变化使旧请求失效，并启动/排队最新搜索。保留旧列表时明确旧范围，不能挂到新筛选下。

**验收**：A 慢 B 快、A 快 B 慢、连续 A→B→A、等待时改查询、旧请求失败均只影响其对应请求；最终列表与可见筛选/查询一致。

### R2 · P1 · 恢复/导入已经成功，刷新失败却显示整个操作失败

**影响/触发**：写入 API 返回成功，后续 `refresh()` 抛错。用户看到“恢复失败”或“导入失败”，可能重复执行已完成的操作。创建备份、导出和删除备份也有相同结果混淆。

**证据**：`app/views/data.js:238–289,324–355` 把写入与刷新放在同一个 catch。真实事件绑定 + mock API 复现：restore/import 各成功一次，refresh 拒绝后，分别显示 `Restore failed`、`Product JSON import failed`。后端 `core/runtime/backup.js:252–318` 的安全副本/回滚并不能修复此界面口径。

**建议**：记录明确写入回执，单独处理刷新；例如“已恢复，页面更新失败。请刷新核对”。保留本次操作 ID/目标与结果，不通过同一按钮暗示重新执行。API 未回执时才表达“结果未确认”。

**验收**：分别覆盖写入拒绝、回执成功/刷新失败、完整成功；恢复/导入成功后失败重试只刷新，不再次写入。创建、删除、导出同源路径一起核查。

### R3 · P2 · 内在活动选择 B，后台与诊断状态仍来自默认智能体 A

**影响/触发**：多智能体环境中切换内在活动的筛选。兴趣/念头按 B 过滤，后台结果、下次检查与 doctor 却仍使用快照单一对象，可能错误地要求修复 B，或遗漏 B 的错误。

**证据**：`core/db/repositories/innerlife/read-models.js:183,234–235,275–276` 在 all 快照中选择默认 profile 的 daemon/doctor。`app/innerlife-actions.js:71–74` 切换只重绘；`app/views/shared-innerlife.js:798–815` 未按 selectedAgentId 核对 daemon/doctor。真实 view 合成复现：选择 B、B focus，最近结果显示 A 的 `A FAILURE`。

**建议**：优先新增/复用按明确 agentId 的只读详情查询；切换后加载该智能体状态，并拒绝旧回执。若状态刻意为全局，应独立标明其范围，不能与单智能体详情混用。

**验收**：A 正常/B 失败，A 暂停/B 启动；快速切换与迟到回执；每项状态能追溯到同一 agentId，查询不得顺便启用后台或生成内容。

### R4 · P2 · 内在活动“阅读全文”实际只展示 800 字符摘要

**影响/触发**：分享正文超过 800 字符。展开后末尾消失，没有截断提示，也没有读取原文。用户无法确认完整内容和限定条件。

**证据**：`core/db/repositories/innerlife/read-models.js:197–214` 把正文截为 800 字符；`app/views/shared-innerlife.js:638–661` 直接从该数组构建“全文”，不再请求详情。临时 SQLite 中原文 1,017 字符，原始查询保有尾标记，阅读快照仅 800 字符，无截断/详情引用字段。history/experience/summary 也有摘要上限，应在整改时检查阅读入口。

**建议**：列表保留摘要；明确选择一条时按 ID 补读有界详情。仍超最终安全上限时标明截断并提供继续读取路径，不把列表摘要改成无限全文。

**验收**：1,017 字符带尾标记记录可完整读到尾部；超安全上限时明确告知；切换条目/智能体期间旧详情不能覆盖新选择。

### R5 · P2 · 一篇超大文档可使同页正常知识文档无法列出

**影响/触发**：目录当前页包含 >512 KiB 的 Markdown。整个列表抛 `document_too_large`，其他正常文档也消失；若恰在第一页，会阻碍首次默认阅读。反向链接扫描遇到该文件也会整体失败。

**证据**：`core/knowledge/library.js:155–169,173–193,266–284`：目录逐项读全文而非独立描述元数据；`map` 和全库 backlinks 扫描未对单文件错误隔离。临时两文件复现：正常文档直接读取成功，同页列表整体拒绝。

**建议**：目录返回正常项及逐项不可读原因，保留总数/分页语义；异常项仍显示路径与原因。大文件全文读取继续受限；不要无提示跳过或假称空库。反向链接失败应保留已取得结果并标明不完整。

**验收**：超大/消失/无权限文件与正常文件混合时，正常条目可访问；限制原因可见；最近文件不可读不冒充“库里没有文档”。

### R6 · P2 · 一部分错误提示没有显示目标，旧成功计时器还会清掉新错误

**影响/触发**：记忆搜索失败、降级或分页失败，调用 `showCopyNotice(message)` 未传 target；函数直接返回，用户只见旧结果或控制台错误。另一次复制/成功提示后 1.8 秒内发生新错误，旧 timer 会清空新消息。

**证据**：`app/memoria-actions.js:41–44,67–70`；`app/views/memoria.js:1762–1765`；`app.js:1406–1411`。受控 timer 复现：先 copied，再写 NEW FAILURE，执行旧回调后 notice 为空。设置概览已单独使用 revision timer，证明问题没有在所有提示处统一修复。

**建议**：在对应列表/弹窗给固定状态节点；错误持久到重试/恢复/主动关闭，成功才自动消失。每个 target 自有计时器与版本；不要扩大为全局 toast 系统。

**验收**：搜索失败、向量降级、分页失败均有可见提示；“成功→错误”“连续两次成功”“离页再回”不会被旧计时器擦除当前状态，保留旧结果时标明。

### R7 · P2 · 后台有终止失败时，状态弹窗仍可能说无需恢复

**影响/触发**：doctor 检出 afterthought 终止失败，但 daemon 的 failureCount 为 0/缺省。整体状态显示 error，下方绿色提示却是“当前没有需要处理的恢复任务”。afterthought 的重试计数和 daemon 失败计数是不同来源。

**证据**：`core/db/repositories/innerlife/read-models.js:420–427` 可独立产生 terminal failure issue；`app/views/shared-innerlife.js:664–674` 仅依赖 daemon.metadata.failureCount 决定肯定性结论。合成 doctor=error、terminal failure、failureCount 缺省，复现该相互矛盾提示。

**建议**：恢复结论基于 doctor issues/afterthought 状态；无证据时“状态未确认”，不能用缺省 0 推导正常。界面只给已有修复入口/必要说明，不增加自动重试副作用。

**验收**：daemon 正常但 afterthought 终止失败、等待重试、模型未配置、状态缺失、确实正常分别表达，只有确认无恢复任务才给肯定提示。

### R8 · P2 · 共同线“全部”目录实际最多 100 条，没有后续入口

**影响/触发**：活跃或归档共同线超过 100。旧话题在目录和本地智能体筛选中不可达；显示的“全部 N 条”和数量其实是载入样本数。

**证据**：`core/db/repositories/continuity.js:395–397` 两个目录固定 limit=100；`core/db/repositories/continuity/lines.js:230–256` 该方法没有 offset。`app/views/shared-innerlife.js:451–483` 只在已有数组内筛选和展示“全部”。首页概览另只取 30 条，但转到共同线后仍受 100 上限。已有 `listContinuityLineSummaries` 具备查询/分页能力，可作为复用起点。

**建议**：让 Desktop 目录使用有 total/hasMore 的摘要分页，智能体筛选在服务端先做；保留当前准确 ID 详情和不激活话题的约束。

**验收**：101+ 活跃与归档条目均可逐页到达；筛选可找到全局第一页之外的智能体/话题；数量不冒充总量，翻页不改变激活线。

### R9 · P2 · 内在活动先取全局样本再按智能体筛选，可能把“未载入”当“没有”

**影响/触发**：A 的近期记录占满全局限额，B 有更早记录。选择 B 时可以显示空态，即使数据库里有 B 的念头/会话。技术详情称“全部记录”，实际仅初始 10/20 条且无加载更多入口。

**证据**：`core/db/repositories/innerlife/read-models.js:208–219` 对 all 查询限额后，`app/views/shared-innerlife.js:764–795,807–813` 才本地筛选。unshared 还先取最近 100 个所有状态，再筛未分享并限 20。会话/输入/任务虽带 page 信息，`app/innerlife-actions.js:41–69` 的 loadMore 方法未被当前 DOM/app 绑定调用。未分享入口却称“查看全部”。

**建议**：查询时传明确 agentId/status，再分页；展示“已载入/总数”和继续读取。若不提供完整历史，直接称“近期记录”，不能让空样本推导为空库。

**验收**：A 21 条新记录 + B 旧记录，切 B 能读到 B；超过初始页可以继续；已分享密集时不会挤掉未分享记录；保持查询只读。

### R10 · P2 · 回召详情在 NOOP 时仍声称重新执行检索

**影响/触发**：自动回召关闭或当前轮不需历史，stageA=NOOP、没有 cache hit。步骤 1 写“跳过记忆检索”，步骤 2 仍写“重新执行了记忆检索”，与实际决策相冲突。

**证据**：`app/views/memoria.js:149–154` 第 2 段只用 `cacheStatus === 'hit'` 做二选一，未检查是否执行检索。此为直接渲染分支确认，没有据此重新推断真实宿主使用情况。

**建议**：按阶段证据表达“未执行”“执行并命中缓存”“执行未命中”“执行失败/降级”“未记录”。缺少 stage 信息保持未知。

**验收**：NOOP/RETRIEVE/错误/未知及缓存命中分别有互不矛盾的路径；无记录不显示“重新执行”。

### R11 · P3 · 英文模式仍显示大量中文正文与按钮，中文模式也混杂装饰性英文

**影响/触发**：切 English 后，记忆回召原因、详情、内在活动状态/规则和多个 aria-label 仍为中文；切中文仍有 CONNECTIONS/UNDER THE SURFACE 等装饰英文。产品支持的语言入口与实际覆盖不一致。

**证据**：`app/views/memoria.js:104–205,1289–1328`、`app/views/shared-innerlife.js:638–700,785–795`、`index.html:125–146,464–477`。现有部分 t() 化不覆盖这些动态字符串；不是只检查翻译字典 key 对齐就能发现。

**建议**：按真实渲染路径迁移文案与可访问名称，保留原始来源/技术值；中文读者不需要的装饰英文可直接删除，避免增加一层重复小标题。

**验收**：双语空态、错误、筛选、正文详情、回召说明、关闭/返回名称均符合所选语言；来源原文不被机器翻译或改写。

### R12 · P3 · 概览查询预算回归仍存在，常规 check 没覆盖

**影响/触发**：现有 overview 专项的固定合成数据。31 次 SQL 超过既有 30 次上限，属于确定的预算回归；本轮没有证明它已造成实机卡顿。

**证据**：直接执行 `node core/tests/overview-snapshot-performance-smoke.js` 退出 1：`Overview exceeded 30 SQL reads: 31`（测试第 70 行）。`npm run check` 退出 0；`package.json` 未把这个运行检查纳入 check，`check:performance` 仅检查该文件语法。

**建议**：先测量重复 query 并合并可复用读，修复后将专项接入适当的常规/发布检查。不要为了绿灯把 30 改 31；若预算确需调整，提供成本与延迟证据。

**验收**：既有 fixtures <=30 次、payload 阈值仍满足；再测一次代表性大数据延迟。预算通过和用户体感验收分别报告。

### R13 · P3 · 通用 openPath IPC 把系统打开失败返回成 true

**影响/触发**：系统 `shell.openPath` 返回错误字符串，renderer 收到 true；备份目录/文档入口可能无反馈。新托盘代码已正确检查，不是同一个缺陷。

**证据**：`electron/ipc-handlers.js:584–587` 忽略返回值；mock shell 返回 `Synthetic OS failure`，真实注册 handler 返回 true。`app/views/data.js:382–385` 调用后也不处理结果。

**建议**：与 `electron/main.js:646–657` 托盘保持一致，错误字符串转明确失败，并在调用入口显示原因；保留成功无弹窗。

**验收**：正常路径、缺失路径、权限/关联程序失败分别返回准确结果；测试仅 mock 系统接口，不要求本轮打开任何文件夹。

## 待确认项与明确保留的实现

1. **真实排版/键盘/原生托盘**：本轮未打开 GUI。最小窗口为 `electron/main.js:674–675` 的 1120×640；再看 1440×900、深/浅主题与长内容。用户旧截图证明旧包体验，不能证明当前包仍有相同缺陷。连接页隐式 Grid 列、关闭按钮错排等旧问题不重复列作已证实缺陷。
2. **知识错误跨 IPC 的 code**：renderer 的缺失文件回退依赖 error.code，内存 API mock 会保留自定义属性；真实 Electron 传输形状尚未验证。后续用隔离实例验证 missing/permission 的端到端错误合同，再决定是否统一结构化 error envelope；本报告不先断言真实回退已失效。
3. **大知识库耗时**：`core/knowledge/library.js:173–193,266–284` 同步目录遍历/排序与反向链接全库读取位于主进程 IPC 路径。算法成本确定，阻塞时长和何种库规模需要缓存/worker 尚无基线；不把它写成已实测卡顿。优先复用结构索引/按 mtime 缓存，测量后再选方案。
4. **设置与更新真实效果**：模型测试可能发请求；新安装生成默认关闭、原配置保留，本轮 check/本地 mock 不能证明厂商 API、登录启动、重启后数据目录和真实更新下载都已接受。保持协议级兼容方向，不增加品牌专页。
5. **恢复结果与恢复能力分开**：后端临时数据专项通过，但不代表用户个人库/外部知识库/密钥文件已经做过完整灾备演练。本轮不执行个人数据恢复。R2 是已复现的结果口径错误，不是后端恢复已损坏的结论。
6. **已修路径不退回旧方案**：知识默认最近修改、按库恢复位置、明确丢失后回退；模型并列分区独立保存/跨区草稿；连接材料复制版本保护；共同线按准确 ID 读取/复制、显式空下一步不复活旧计划；日志区分返回/送达/使用；托盘启动重载队列。常规 check 中相应专项通过，应作为后续回归基线。
