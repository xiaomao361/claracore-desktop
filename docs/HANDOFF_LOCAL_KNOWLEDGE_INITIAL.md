# Desktop 本地知识库接入 handoff

状态：供 Desktop 项目继续讨论与实施；本文件记录已表达的需求、当前实现和待定设计，不表示功能已完成。

2026-09-22 更新：本文件保留初始讨论记录。现行实施顺序与收录职责见
[`V0.8.0_LOCAL_KNOWLEDGE_PLAN.md`](V0.8.0_LOCAL_KNOWLEDGE_PLAN.md)。
收录是 v0.8.0 的核心闭环：Agent 整理来源、段落与关联，Desktop 提供受约束的写入、
检查、索引和阅读结果；不再把收录放在纯阅读与检索全部完成之后。

## 目标与已表达的要求

用户希望将个人知识库纳入 ClaraCore Desktop，与 Memoria、共同线（Shared Line）和 InnerLife 并列呈现，并在现有回召入口统一判断何时查记忆、何时查知识。知识库不是另一个独立 App。

- Desktop 增加可供人阅读的「知识」模块，支持选择本地知识库目录。当前资料在 `/Volumes/E61/Knowledge`；这是现有资料位置，不应成为硬编码路径。
- Markdown 文件是知识正文的唯一权威副本，保留在用户所选磁盘目录。Desktop 可保存目录设置，生成可重建的索引或阅读缓存，但不能为了展示或检索另存一套正文。切换目录不应默认移动、复制或覆盖原文件。
- 知识按完整意思分段，保留来源、日期、观点归属与不确定性。正文中的关联链接指向其他文档的具体段落；阅读界面能够点击跳转，并可显示由正向链接推导的反向链接。
- 支持精确与语义／混合查询，研究和回顾时优先利用本地资料。Jev 用于辅助检索路由的想法已经提出；当前隐私边界是 Jev 只接收查询文本，知识正文、文档路径、搜索结果和对话历史均不发送给它；向量在本机生成。
- 入库包括主动交给 Agent 的材料与实质话题结束后的选择性被动收集。两者使用同一套清洗、分段和链接流程；这不意味着后台监控应用、浏览历史或所有对话。

## 四个领域的建议边界（待在 Desktop 项目确认）

| 领域 | 回答的问题 | 典型内容 | 不应承担 |
| --- | --- | --- | --- |
| Memoria／记忆 | 关于用户及共同经历，哪些已确认事实、偏好和决定值得长期记住？ | 用户明确的稳定偏好、共同作出的决定、可追溯的个人事实 | 存放整篇研究材料或把未采纳观点写成用户立场 |
| 共同线／Shared Line | 这件共同工作现在走到哪里，下一步是什么？ | 当前目标、已核实的位置、阻塞与下一步 | 充当永久资料库或历史文章副本 |
| InnerLife／内在活动 | Agent 自己形成了什么联想、疑问或待分享的想法？ | 念头、关联尝试、分享状态 | 未经核实就宣称为用户事实或知识结论 |
| Knowledge／知识 | 有哪些可再次阅读、检索、追溯和相互链接的资料与理解？ | 来源材料的清洗段落、方法、解释、比较、未解决问题 | 自动替用户背书，或取代当前任务进度 |

同一主题可以在四处各有**不同职责的引用**。例如知识文档保存某方法及证据；Memoria 只记录用户明确采用该方法的决定并指向文档；共同线记录当前实践进度；InnerLife 的相关想法在被核实或采纳前保持为想法。不要靠复制正文制造跨模块关系。

初始核对时 [`POSITIONING.md`](POSITIONING.md) 把 *formed knowledge* 列入 Memoria 的稳定节点。v0.8.0 计划启动时已修订定位文案，明确「已确认、关于我们」的记忆与「有来源、可探讨」的知识之间的边界；这仍是产品定义，不表示知识模块已实现。

## 已核对的现状

- Desktop 当前导航已有 Memoria、Shared Line、InnerLife，没有独立知识模块。`gateway_auto_context` 是每轮自动上下文入口，当前只收集 Memory 候选，最多选择一个有界块；InnerLife 不自动投递。Memory Controller 默认关闭自动回召，可在观察模式记录判断。参见 [`README.md`](../README.md)、[`system.js`](../core/gateway/tool-handlers/system.js)、[`turn-context.js`](../core/gateway/turn-context.js) 和 [`auto-context.js`](../core/gateway/auto-context.js)。
- Desktop 已有目录选择的 Electron IPC 先例，但不是知识库设置：[`ipc-handlers.js`](../electron/ipc-handlers.js)。
- 现有知识工具在 `/Volumes/E61/Projects/knowledge`。`kb.py` 使用配置中的 `root` 和 `index`，提供精确、语义、混合搜索、段落读取、链接检查与索引构建；索引和静态阅读页位于 `/Volumes/E61/KnowledgeIndex`，均可从 MD 重建。Jev 当前仅对查询文本给出 shadow 建议，实际 `auto` 检索仍按确定性规则执行。参见 `/Volumes/E61/Knowledge/README.md` 和 `/Volumes/E61/Projects/knowledge/README.md`。
- 先前在 Codex 对话里给出的静态 HTML 段落链接有用户反馈「点击打不开」。无锚点链接虽已重新给出，尚无用户侧成功确认。Desktop 内的 MD 阅读与链接跳转应做真实交互验证，不应把文件存在或静态生成成功当作可点击验收。

## 初始建议的最小实现顺序（已由 v0.8.0 计划替代）

1. **只读接入与阅读**：选择并保存目录；校验目录及 MD 结构；浏览文档、渲染段落、打开内部链接与反向链接。以 E61 当前知识库做真实样例，不迁移或重写正文。目录未挂载、无权限、空库、索引过期应是可区分的状态。
2. **显式检索接口**：复用或封装现有知识工具，提供精确、语义、混合查询及按段落读取；返回文档相对路径、稳定锚点、来源和索引状态。先保证 Agent 可以显式查、用户可以在 Desktop 打开结果。
3. **统一回召决策**：在 Desktop 的现有入口上评估「无检索／记忆／知识／两者」和每个领域的查法。它不应是互斥的“记忆精确／记忆向量／知识精确／知识向量”四选一；一个请求可能需要两域。用户明确指定的领域或方式优先。知识长段落先返回有界摘要与读取指针，按需展开，避免塞满当前自动上下文块。
4. **Jev shadow 对照**：只给查询文本与固定的选项定义，不给正文、路径或历史。用真实查询比较既有规则与 Jev 建议，记录漏检、误检、双域需求、延迟及失败；低置信度、超时、格式错误和不可用保留既有安全路径，并与真正「无结果」区分。是否让 Jev 控制实际路由，需要另行根据结果决定。
5. **入库协同**：检索入口稳定后，再考虑从 Desktop 呈现待整理材料与清洗结果。Agent 仍负责判断、来源核对及有意义的链接；不能把检索命中自动写成新记忆或知识，也不能把 InnerLife 的念头自动转成事实。

## 初始待定问题与当前处理

现行首版取舍见 v0.8.0 计划：一个当前目录；Agent 与 Desktop 共用收录通道，
页面可查看收录与待整理结果；外部编辑器仍可修改 MD；旧知识卡保留原件与指针。
以下问题保留当时的讨论背景，不再作为第一阶段的阻塞清单。

- 首版只支持一个当前目录，还是管理多个知识库目录？当前需求只明确「可选择本地路径」。
- Desktop 首版只是阅读／搜索已有 MD，还是也承担 Agent 入库后的检查与展示？MD 的人手编辑入口是否仍交给外部编辑器？
- Memoria 中既有「知识卡」如何在新模块中表示：保留历史原件与指针，还是逐项核对后建立交叉引用？不应做无差别自动搬迁或删除。
- 自动回召中知识候选何时与记忆候选并列，何时只给可继续读取的文档指针？需要用实际问答和用户可见结果验收。

本 handoff 没有授权修改现有 Memory、共同线、InnerLife 数据，迁移原始卡片，启动后台采集，或改变 Jev 的隐私边界。项目实现时按当前代码与真实试用结果细化以上建议。
