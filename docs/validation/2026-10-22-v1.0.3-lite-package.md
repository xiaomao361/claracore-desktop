## Verified behavior

The original reproduction used an active non-restricted memory whose existing
embedding row was pending, with matching timestamps (not stale). Before this
fix its maintenance report returned `ok` and missing=0. The nightly runtime
path still consumed it successfully, so the claimed absence of nightly repair
was not reproduced. The defect was audit visibility, not a missing scheduler.

The final build separately counts `pendingEmbeddings`. Only pending work gives
maintenance status `pending` and combined audit `needs_review`; actual repair
issues retain `needs_repair`. Pending does not establish that a job is stuck.
No timeout threshold or new scheduler was introduced. Existing pending rows are
not reset/requeued merely to surface them in the audit.

Runtime `after` now reads after the actual processing batch. Tests prove ready
completion, remaining pending work with a bounded batch, and failed provider
results stay distinguishable. Disabled processing preserves pending, while dry
run leaves all embedding rows unchanged. Restricted, archived and deleted
memories are excluded. An offline Home regression verifies a pending reminder
is counted once and an independent repair issue remains visible.
