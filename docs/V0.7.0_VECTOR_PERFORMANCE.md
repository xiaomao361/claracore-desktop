# 0.7.0 向量检索性能诊断

## 当前结论（2026-09-09，0.7.2 已安装）

默认引擎已切换为 `sqlite-vec`；Migration 011 已实现按变化 ID 增量同步。
此前“更新后全量重建”的问题已修复。以下为已有诊断样本，不是正式 p95：

- 400 条合成向量：首次 107.8ms，热查询约 3ms，单条更新后查询 4.4ms。
- 50k 合成向量：单条更新后查询从约 23.3s 降至 293.5ms；首次构建仍约 16.8s。
- 真实副本两个模型空间共 60 组结果 ID/分数对照一致；首次 native 查询分别
  297.9ms / 150.8ms。原始记忆与 embedding 摘要保持一致。
- 0.7.2 已安装 ASAR 的 Node/SQLite CLI 原生扩展、增删改同步测试通过。
- 这些检索计时不含在线生成查询向量；自然语言端到端搜索不能据此宣称只需几毫秒。
- 完整 50k 旧新引擎对照、Windows 及长期使用体验仍未验收。

来源：`out/sqlite-vec-profile-trial-400.json`、`out/sqlite-vec-profile-incremental.json`、

## 历史诊断（2026-09-08）

以下保留当时 legacy 默认、增量同步前的诊断过程；未完成项和后续动作以本文顶部为准。

## 已确认的瓶颈与修改

50k 热查询的主要瓶颈是资格过滤读取原始向量表，不是分数精度校正。
原执行计划从 memories 状态索引出发，逐条按 memory_id 查询 embeddings，
为判断 provider/model/dimension/status 读取带大段 JSON 的数据页；Agent 标签
判断也发生在这些读取之后。10% 过滤因而没有避免绝大部分回表成本。

Migration 010 新增普通 SQLite 覆盖索引：
`memory_embeddings(provider, model, dimension, status, memory_id)`。
新执行计划显示 `USING COVERING INDEX idx_memory_embeddings_space`，资格判断
不再读取原始向量载荷。此索引也供 legacy 使用；后面的引擎对照在相同新 schema
上运行，不把 legacy 固定在缺少索引的旧 schema 上。

投影重建的临时表改为只存 ID 与校验结果。合法向量在同一源锁事务内读取、
插入 vec0；不再把完整 JSON 写入临时表后反复扫描。原始 JSON、过滤规则、
0.55 阈值、精度复核、同分排序、候选扩容和可识别失败状态保持原有契约。

## 分段证据

Apple M4 / darwin-arm64 / Node 22.23.1，512 维确定性合成集，无日用数据。
同一个 query vector(0)，每个过滤场景重复 5 次；这是定位瓶颈的实验，不是正式 p95。
embedding 生成被替换为固定向量，完整搜索包含关键词查询与结果整理。

| 50k 阶段 | 无覆盖索引 / 100% | 有覆盖索引 / 100% | 无覆盖索引 / 10% | 有覆盖索引 / 10% |
| --- | ---: | ---: | ---: | ---: |
| eligible CTE | 1,708 ms | 16.5 ms | 2,096 ms | 28.1 ms |
| nearest CTE（含过滤） | 1,831 ms | 137.9 ms | 2,185 ms | 51.4 ms |
| scored CTE（含前序） | 2,337 ms | 147.8 ms | 2,145 ms | 53.2 ms |
| 完整热查询范围（5 次） | 1,957–2,151 ms | 156–198 ms | 1,830–1,919 ms | 71–74 ms |

各 CTE 单独执行，计时是累计且执行计划可能不同，不能相加或当作精确可加的耗时分摊。
覆盖索引前后的结果来自 `out/sqlite-vec-profile-before.json` 与
`out/sqlite-vec-profile-indexed.json`。正式热查询结果以正式基准节为准。

首次建投影的逐语句诊断：临时表生成约 12.74 秒，读取问题记录约 1.58 秒，
vec0 插入约 1.82 秒。取消临时表中的原始 JSON 后，问题扫描变为轻量操作，
首次完整搜索约 14.63 秒，仍不能满足无感冷启动。来源为
`out/sqlite-vec-profile-build.json` 与 `out/sqlite-vec-profile-compact-build.json`。
这些是单次合成测量，不是稳定冷启动 p95，也不是磁盘冷缓存基准。

## 正式样本基准（对照未全部完成）

每个规模、每个过滤场景 20 次热查询，查询向量为固定种子序列 `vector(i * 10)`，
两个引擎在独立进程中串行运行；期间没有并行运行本任务的构建或其他性能测试。
同一规模的两个引擎使用相同语料和包含 Migration 010 的 schema。

| 向量数 | 合格比例 | legacy p95 | native p50 | native p95 | native 首次查询 | 样本 ID 对照 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 1000 | 100% | 105.08 ms | 4.50 ms | 4.84 ms | 254.23 ms | 通过 |
| 1000 | 10% | 8.62 ms | 2.62 ms | 2.77 ms | 2.04 ms | 通过 |
| 10000 | 100% | 15,186.57 ms | 30.23 ms | 30.54 ms | 2,344.07 ms | 通过 |
| 10000 | 10% | 504.54 ms | 15.03 ms | 15.75 ms | 13.78 ms | 通过 |
| 50000 | 100% | 整批 300 秒超时 | 154.85 ms | 175.25 ms | 13,472.03 ms | 未完成 |
| 50000 | 10% | 整批 300 秒超时 | 72.85 ms | 85.27 ms | 77.98 ms | 未完成 |

只有每个规模的第一个 native 查询包含建投影；10% 场景的首次查询复用已建投影。
1k 没有回退，10k 两种过滤场景均超过预设 30% 改善要求，且样本 ID 一致。
50k legacy 的超时发生在整批测量，不能当作单次延迟下界，也没有完整 p95 或
跨引擎 ID 比对；**整份报告状态为 incomplete，退出码为 1，A3 仍未通过。**
不能把完成的 native 测量当作完整跨引擎验收。

native RSS 快照约 72–90 MiB，不是峰值。真实语料、更多有语义近邻/近分数的查询、
峰值内存和跨平台性能尚未验收。原始数据：`out/sqlite-vec-baseline.json`；
覆盖索引前的 5 样本探索报告另存 `out/sqlite-vec-baseline-before-space-index.json`，
不将不同样本数、不同 schema 的数据拼成一次正式对照。

- `npm run check` 通过。此次修改之后尚未重新打包；此前 unsigned Mac Full/Lite
  包内通过的结果只覆盖上一阶段代码，不宣称是此次新索引的包内验证。
- HCT-2026-09-08-02：按既定过滤、排序与原始数据保持规则验证迁移与检索结果；
  HCT-2026-09-08-01：无效向量/故障仍保留失败状态及独立关键词结果。此次是检查
  运行证据，不宣称试验已证明长期可靠性。

50k 单条更新实测：反转 `fixture-000000` 的向量后，下一次搜索耗时 **23,338 ms**，
revision 变为 50001，投影仍有 50000 行，已确认不再返回被改变向量的旧命中。
逐语句记录中，全量校验约 13.36 秒，删除旧投影约 1.91 秒，重新插入约 7.53 秒。
该诊断首次查询为 16.52 秒；与正式基准的 13.47 秒及早先 14.63 秒一起说明冷路径
存在波动，不能仅据一次测量声称冷启动已稳定改善。证据：
`out/sqlite-vec-profile-rebuild.json`。因此热路径改善不解除重建阻塞问题。

全局 embedding revision 变化仍会使整个被查询空间重建，即使只更新一条向量，
或只更新 embedded_at。进程重开仍从空投影开始。下一步应单独设计与验证增量同步，
覆盖删除、空间切换、无效变有效、跨连接变更、恢复和中断后的重建；同时处理
首次构建阻塞。不能通过吞错、默认返回空结果或减小候选范围掩盖这些成本。

## 复跑

```sh
npm run test:sqlite-vec:projection
CLARACORE_VEC_BASELINE_TIMEOUT_MS=300000 npm run baseline:sqlite-vec
npm run profile:sqlite-vec -- 50000 current
CLARACORE_VEC_PROFILE_NO_INDEX=1 npm run profile:sqlite-vec -- 50000 no-index
CLARACORE_VEC_PROFILE_BUILD=1 CLARACORE_VEC_PROFILE_MUTATION=1 npm run profile:sqlite-vec -- 50000 rebuild
```

所有语料与投影均为临时目录，结束时清理。`NO_INDEX` 仅移除本次生成语料的索引。
`BUILD` 在固定合成 SQL 中分拆语句计时，会改变调用开销；生产 SQL 执行方式不变。
`MUTATION` 改变一条合成向量并确认下一次搜索没有陈旧命中。
完整原始 JSON 报告保存在忽略 Git 的 `out/`；本文件保留可评审的主要证据。
